# V1-S3-007-PR2 validation — correlated platform telemetry verification

Change: the questions an operator would ask of a store holding what the `inferops-llm`
chart's scrape configuration would collect are published as a checked record, twenty-
three of them; the labels, series, joins, and answerability claims each one depends on
are derived from the accepted telemetry catalog and the collection record rather than
listed by hand; and every query is evaluated against six synthetic stores whose series
carry the label sets the committed renders would attach. Ten deliberately wrong
queries are committed beside them, each naming the rule that refuses it.

**Evidence class.** Everything asserted here is `local-static`: files parsed, derived,
compared, evaluated by this repository's own code, formatted, linted, type-checked,
and driven through documents that already exist. **Nothing has been collected and no
query has been answered.** No collector, store, dashboard, or alerting path is
selected, nothing scrapes either InferOps endpoint, this chart has never been
installed, no InferOps API image is published, and **no Prometheus has parsed, loaded,
or evaluated a single expression in this change**. The maximum certification a
`local-static` result may carry is `C0`, and that is what this carries.

## What this record does not establish

- **That any query has been answered.** Every result was produced by the declared
  PromQL subset evaluator in `tools/telemetry_correlation/evaluate.py`, over fixture
  series written by hand. No engine ran any of it.
- **That the evaluator agrees with Prometheus.** It implements a declared subset with
  declared differences, chiefly that `rate()` and `increase()` do not extrapolate. The
  fixtures place their samples on the window boundaries, where the two agree, and that
  is an argument rather than a measurement. `promtool` is **not** installed on this
  host and was **not** run; see *Not run* below.
- **That the fixtures resemble a real scrape.** Their label sets were written to match
  the relabelling the committed renders perform, and a test compares the label
  vocabulary against the catalog and the collection record — but discovery, `keep`
  filters, port selection, and target-label assignment are not simulated. A fixture
  *states* what a target would carry.
- **That the recording rules work.** They are read from the committed render and
  evaluated here at each fixture instant in render order. No collector evaluates them,
  no group interval is honoured, and staleness between evaluations is not modelled.
- **That an operator would find these queries useful.** No operator has run one, and
  there is no store for one to run against.
- **That the collection gaps are closed.** Four are published, and this PR closes
  none of them.

## What was built, and the decisions in it

### A parser, because a list beside each query would be a second copy

The record could have listed, beside every expression, the metrics it reads and the
labels it groups by. That list is a copy of the expression maintained by hand, and the
first edit that forgot to update it leaves a record describing a query nobody runs.
Everything the checker knows is **derived from the expression** by
`tools/telemetry_correlation/promql.py`, so the two cannot disagree.

The subset it accepts is declared: five aggregations, five functions, the set
operators, arithmetic, comparison, and explicit vector matching. **An expression
outside it raises rather than parsing to something different** — which is the whole
safety argument for reading a query here instead of in Prometheus. A form this cannot
represent cannot be quietly mis-evaluated, because it cannot be represented.

`topk`, `bottomk`, and `quantile` are excluded because they select rather than
summarise, so their answers depend on tie-breaking the evaluator does not model.
`count_values` is excluded because it writes a label out of a *value*, which is the one
move the telemetry catalog exists to prevent.

### Six rules, and the vocabulary derived on every run

| Rule | The failure it prevents |
|---|---|
| `query-expression-is-outside-the-verified-subset` | A published expression nothing here can read, which every other rule would be vacuously satisfied by |
| `query-names-a-label-the-catalog-bars-from-a-metric` | A query asking for a label the collector drops on the way in, which returns nothing forever while reading as a question somebody could answer |
| `query-names-a-label-nothing-in-this-release-carries` | A grouping key no series has, which collapses every series into one row keyed on nothing |
| `query-reads-a-series-nothing-in-this-release-produces` | A query against a name nothing publishes, indistinguishable in a dashboard from a query against a quiet system |
| `query-claims-an-answer-a-signal-nothing-emits-cannot-give` | A well-formed query with a dishonest label on it: the metric is in the catalog and marked not emitted, so a collector would not make it answerable |
| `join-matches-on-a-key-one-side-cannot-carry` | A join whose `on` set names a label the one side does not have, which drops every element and returns nothing |

The permitted label vocabulary is **recomputed from the catalog and the collection
record on every run**: every attribute whose placements include `metric-label` or
`info-label`, every target label the collection record declares, and `le`. A test
asserts that this set and the chart's rendered `labeldrop` list are complements
derived from one decision — if they ever disagreed, a query could ask for a label the
collector removes, which is exactly the empty panel with no explanation.

### The queries are run, not only read

Six synthetic scenarios, each a set of series carrying the label sets the render's
relabelling would attach. Each store goes through the collector step the chart
actually renders (`labeldrop`, read as the alternation the chart writes rather than
executed as a regex), then the chart's recording rules are read from the committed
render and evaluated at every fixture instant in render order, and then every query is
evaluated.

That last part is what makes this PR verification rather than description. Three
findings came out of running them that reading could not have produced:

1. **`throughput-joined-to-build-identity` returns nothing, not a partial answer**,
   when a target is up and publishes no identity. The scenario
   `api-target-up-without-identity` shows the throughput query returning rows and the
   join returning none — which is why `inferops:build_info_absent:platform_api` is the
   query that explains it.
2. **A cross-tier identity join is not possible at all** with more than one API
   replica. `inferops_build_info` is one series per API process, and the labels a
   runtime series shares with it are the same on every replica, so the match is
   many-to-many. This is published as the gap `no-cross-tier-identity-join` and a test
   drives the evaluator into the error to prove it.
3. **The chart's default leaves `service_version` empty**, and an empty label value is
   indistinguishable from an absent one in Prometheus, so `group_left(service_version)`
   copies nothing rather than copying a blank. Stated in the query document; the
   fixtures model a release that set it.

### The honest half

Four queries return nothing however long anybody waits —
`model-readiness-by-workload`, `model-load-duration-p95`, `queue-wait-p95`, and
`api-process-memory-by-replica` — and two have no expression at all, because there
is no series to select: `container-and-pod-resource-use` and
`pod-phase-restarts-and-container-readiness`.

They are published rather than omitted. A question missing from a query catalogue is a
question somebody writes badly, gets an empty panel for, and reads as health.

Four catalog metrics have no query at all, and the record says why for each: the
contract validator is a library with no process to scrape, and three are deferred out
of V1 by the catalog itself. A test asserts that the set of catalog metrics no query
reads is exactly the set the record accounts for, and that every one of the eight
metrics the catalog marks **emitted** is read by a published query.

## Not run, and why

- **`promtool`.** It is not on `PATH` on this host, it is not pinned anywhere in this
  repository, no gate runs it, and `CONTRIBUTING.md` does not require it. Installing it
  would have made a cross-check of this repository's evaluator against the real PromQL
  engine possible — `promtool test rules` can evaluate an expression against synthetic
  series — and that check would be worth having. **It was not done, and nothing in this
  change may be read as having been checked against a Prometheus.** It is recorded as
  the first follow-up below.
- **Any real Kubernetes execution.** The brief permits a real local Kubernetes run
  "when authorized". No such authorization was given for this change, no cluster was
  contacted, and no `kubectl`, `helm install`, or scrape was run.
- **Any collector.** None is selected. Nothing was installed, started, or pointed at an
  endpoint.
- **Any model or runtime.** No weights were read and no runtime process was started.
- **Dashboards and alerts.** Explicitly out of this PR's boundary. No panel and no
  alerting rule was written.

## Deferred work and follow-up dependencies

1. **Cross-check the evaluator against `promtool`.** Generating a `promtool test rules`
   file from the same fixtures and expressions would put this repository's semantics
   beside the real engine's. Not done here; `promtool` is not a repository dependency.
2. **The four gaps**, none closed by this PR: `no-cross-tier-identity-join`,
   `no-resource-correlation`, `no-readiness-or-model-load-signal`, and
   `no-trace-correlation`. The first three would need the serving-runtime adapter
   instrumented or a cluster add-on this chart does not own; the fourth needs ADR 0006
   D1's implementation half.
3. **Dashboards and alerts**, which are deliberately not in this PR and have no owner:
   an alert needs a receiver, a routing tree, and somebody on the other end, and none
   of the three is decided.
4. **A collector**, which is the open question ADR 0004 carries. Until one exists,
   every query here returns nothing for the same reason.

## Risks, assumptions, limitations, and blockers

- **The evaluator is the largest new surface and is unverified against the engine.**
  It is bounded by a declared subset and refuses anything outside it, its differences
  are declared, and 319 tests exercise it — but a semantic disagreement with Prometheus
  inside the subset would not be caught by anything here. Follow-up 1 is the mitigation
  and it is not done.
- **The fixtures are the assumption the whole scenario half rests on.** Their label
  sets are checked against the catalog and the collection record, so a fixture cannot
  carry a label the design forbids; nothing checks that a real scrape would produce
  these *values*, because there has been no real scrape.
- **`histogram_quantile` is a reimplementation.** It interpolates linearly inside the
  chosen bucket and returns `NaN` without a `+Inf` bucket, which is the engine's rule,
  and it does not repair non-monotonic bucket counts.
- **The recording-rule evaluation order is the render's order.** A rule reading an
  earlier rule's output sees the history it would have had. A collector's group
  interval is not modelled.
- No blocker.

## Independent review before push

Two independent reviews were run against the first commit on this branch, one for
correctness and one for security and information disclosure. **They found seven
defects, and all seven are fixed in the second commit.** Every one was found by
reading; none needed a Prometheus, which is the point worth recording, because a
cross-check against a real engine is still the follow-up that has not been done.

| # | Severity | What was wrong | Fix |
|---|---|---|---|
| 1 | High | `join-matches-on-a-key-one-side-cannot-carry` read only the `on` set, so a `group_left`/`group_right` written with `ignoring` was **not checked at all** — the rule read as enforced for a syntax the subset accepted and the document advertised | The parser now refuses a group modifier without an explicit `on`. The join key has to be written down, because the rule that reads it cannot check what a key *is not* without guessing what it is |
| 2 | High | The validation record said **twenty** barred labels; the catalog derives **nineteen**, and the test that asserts them collects nineteen cases | Corrected in both places it appeared |
| 3 | High | The document and the record's `an-empty-result-is-the-common-answer` limitation said **three** always-empty queries; there are **four**. The commit message and changelog already said four, and this record patched around the stale number mid-sentence | Corrected in the record, the document, and this record |
| 4 | Medium | A comparison without `bool` dropped the metric name and reduced the result to the join key. Prometheus drops the name only for the arithmetic operators; a comparison *filters* and keeps the left element unchanged | Fixed, declared in the differences list, and pinned by three tests — comparison, `bool` comparison, and arithmetic |
| 5 | Medium | The evaluator's lookback docstring said "no older than", which reads as inclusive, while the code implements a half-open window | The window is now stated exactly as `(T - 300s, T]`, declared as a difference **this repository has not verified against the engine** rather than as agreement, and pinned by a boundary test |
| 6 | Medium | `group_right` had no evaluator test at all — only a parser one — while the validation record claimed the tests exercised the evaluator | A `group_right` evaluation test was added. The logic itself was traced by the reviewer and found correct |
| 7 | Medium | A broken relative link: `ADR-0004-repository-and-tooling-structure.md` does not exist | Corrected to `ADR-0004-component-and-ownership-boundaries.md`, which is also the semantically right target |

The security review found **no** secrets, personal data, machine-specific paths, or
trace of the private requirements repository, and confirmed the synthetic fixture
identifiers that resemble sensitive values (the model revision and the runtime image
digest) are values this repository already publishes in thirty-odd other files. It
found three robustness defects, all of which contradicted a claim this change makes
about itself, and all three are fixed:

| # | Severity | What was wrong | Fix |
|---|---|---|---|
| 8 | Medium | A deeply nested expression raised `RecursionError`, not `PromQLError` — so the module's "refused rather than published unchecked" contract was untrue for exactly the input a caller could not handle | A declared nesting bound of 100, refused like any other unreadable form, with a test either side of the bound |
| 9 | Medium | Matcher and `label_replace` patterns were compiled straight from input. `up{job=~"(a+)+$"}` hung the process on a 35-character value | Patterns must now be inside a declared safe subset — a literal run, an escaped character, `\|`, and at most four wildcards — with no group for a pattern to backtrack into. Six pathological patterns are refused by test and four real ones still work |
| 10 | Medium | `SAFE_MESSAGE_CHARACTERS` was enforced on a finding's *message* and not its *subject*, which is the record's own `queryId` and reached stdout unfiltered | Every field is filtered now, every identifier in the record is asserted kebab-case, and a hostile identifier carrying an ANSI escape, a carriage return, and a right-to-left override is driven through the checker |

Two low findings were also fixed: `_base_name` stripped a histogram suffix
unconditionally, which would silently mis-map a future metric whose own name ended in
`_count`, and the `or` branch of the static label analysis returns a union that is an
upper bound rather than an exact set. The first is now guarded by a catalog lookup and
a test; the second is documented where it is used, because an upper bound there can
miss a refusal and can never invent one.
