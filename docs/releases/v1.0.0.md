# InferOps v1.0.0

Status: **release notes, prepared in `V1-S5-008-PR1`** from `742355b`. The annotated
`v1.0.0` tag is created only after that change merges and every post-merge check in

`v1.0.0` is the first versioned release of InferOps. The number identifies packaged
repository state and [adds no evidence](../releases.md): every result below is what one
committed record observed, and the release is exactly as strong as the frozen evidence
pack it is cut over. The data behind this page is
[`v1.0.0.v1alpha1.json`](v1.0.0.v1alpha1.json), and `tests/testing/test_release.py` fails
if a digest, a component identifier, a measured figure, or a count of claims, records, or
levels here disagrees with the file it comes from. The other counts written in words, and
the descriptions of what the release contains, are checked by review only.

## The problem V1 investigated

A language model can be made to answer inside a Kubernetes cluster in an afternoon. The
hard part is saying, with evidence, what a caller gets when load rises, when the only
serving pod is lost, or when the model never finishes loading, and which signal an
operator can trust while it happens. V1 built a paved road for one open model behind one
API, then caused each of those situations on purpose and recorded, side by side, what
the callers, the cluster, and the collector each reported.

## What the evidence showed

Every real result here is Docker Desktop's Kubernetes (`docker-desktop`), one Windows
host, CPU only, one replica of each tier. None is a capacity, a service-level objective,
an availability figure, a benchmark, or a cost.

- **More callers bought waiting, not throughput.** From concurrency 1 to 4, completed
  requests stayed between 0.554 and 0.575 per second while median latency rose about
  fourfold, with the runtime serving one request at a time. *Boundary:* one single-slot
  release and one fixed prompt; whether the slot or the processor held the rate was not
  tested.
- **Pod readiness did not describe what a caller could reach.** When the only serving
  pod was deleted under load, 40 of the 41 requests dispatched in a 31 960 ms
  caller-visible outage were refused. At every readiness sample before the replacement
  was observed Ready, the deleted pod still reported `Ready: True` while the Service had
  no ready endpoint. The Service's ready endpoints went to zero with the loss and the
  API's errors named it by canonical code; pod readiness, and scrape health at its first
  readings after the delete, did not. *Boundary:* one replica is the cause of the outage, and a
  second run's outage was 2 832 ms.
- **The deployed topology decides which error a caller meets.** A model held from
  finishing its load stayed alive and unready for 179 755 ms without a restart, and no
  completion came back `model-not-ready`: the runtime pod never became Ready, its Service
  never held an address, and every completion came back `capability-unavailable` with
  condition `runtime-unreachable`. An error contract has to be tested through the
  deployed path, not only in the adapter. *Boundary:* one values overlay, completions
  asked of the API pod through a port forward.
- **Running the whole path is a test in its own right.** From a fresh clone, all
  18 steps completed in 1 h 30 min 32 s of wall clock, across three invocations, on the
  third attempt. The first two attempts stopped on
  five repository defects — among them a test suite inheriting the operator's provider
  selection and a residue check asked once instead of within a bound — and none was a
  host problem. *Boundary:* one run, on one host, by the change's author, an AI coding
  agent; no second engineer has repeated it.
- **Use and reservation diverged in opposite directions.** In the first load run, the
  request path used about 5.4 times the processor time it reserved while most of its
  memory reservation sat idle, so an estimate has to say which of the two it prices.
  *Boundary:* the only prices are synthetic, every cost record has confidence `none`, and
  no cost figure is published.

one narrative, with the architecture, the decisions, and every limitation beside its
finding. Each finding above is a row of its results-first summary.

## What the release contains

- **A workload contract and its tooling.** `WorkloadContract` `v1alpha1`, its schema,
  valid and invalid fixtures, a validator with canonical refusals, a typed platform
  domain, and a scaffolder that writes a contract with its own tests.
- **One inference API with an explicit adapter.** Five ASGI routes; the mock or the real
  adapter is chosen by name, and nothing falls back from real to mock. The claim that the
  mock path declares its own kind and refuses a model identity that is not mock-labelled
  is still `planned`.
- **A pinned serving path.** A digest-pinned `llama.cpp` server and a revision- and
  hash-pinned Qwen3-1.7B GGUF, a resumable hash-verifying model acquisition, a local real
  composition, and a real-runtime certification workflow.
- **A release for a cluster the operator owns.** The `inferops-llm` Helm chart and a
  Terraform prerequisite layer for an existing `docker-desktop` or `kind` cluster, which
  is selected explicitly, verified before anything is mutated, and never created or
  deleted. Only `docker-desktop` has been executed.
- **Telemetry that says when it is absent.** Eight catalog metrics and structured request
  logs from the API, a release-scoped Prometheus collector, a checked Grafana dashboard
  definition, and six alert rules with runbook sections. No installed release evaluates
  the alerts and nothing delivers one.
- **Repeatable experiments.** A versioned load generator, performance scenarios, the
  pod-loss and unready-model experiments, a cost calculation for the estimated basis, a
  clean-clone workflow, and an operator runbook.
- **An evidence system.** A claim and evidence register, the project-defined evidence
  levels `C0` Static to `C4` Operational with a validator that holds each record to its
  level, a generated proof dashboard, an evidence index with a release gate, and one
  continuous-integration lane that runs the default checks on every pull request and
  every push to `main`.

## What it does not contain

V1 is not a production-ready or portable platform, and no record here says it is.

- **One provider, one host, CPU, one replica.** Nothing certifies `kind`, Linux, macOS, a
  GPU, another model, or another runtime version. The multi-replica profile was refused
  at a capacity gate on the measured host.
- **Not defended.** No caller is authenticated or authorized, nothing is rate-limited,
  the network policy the chart renders is not enforced by the clusters this project runs
  on, and twelve security risks are carried rather than reduced.
- **Unbuilt.** Nothing turns a validated contract into release values; a values file is
  written by hand, and serving a workload from its contract alone is `planned`.
- **Not delivered.** No alert reaches anybody, no telemetry is kept past a release, no lane in
  continuous integration installs a release or runs a model, and sustained throughput
  and capacity are deferred out of V1.
- **Not a cost.** No provider cost is claimed or published.
- **Not reviewed from outside.** Nobody outside this repository has reviewed a claim, a
  record, or this release. Its approval is the `repository-maintainer` role's, under
  [ADR 0015](../architecture/decisions/ADR-0015-v1-decision-ownership-and-sign-off-authority.md),
  and that role has one holder.

Seven claims are `planned`, one is `deferred`, and ten are `not-claimed`;
[the proof dashboard lists every one](../proof/dashboard.md#what-v1-does-not-claim).

## What is not published

The release is the annotated tag and the source archives the hosting service makes from
it. Nothing else is published, and in particular:

- **No InferOps container image.** The API and model-seed images are built from the
  checkout and loaded into the operator's node. The records name images built from earlier
  revisions; an image built from the tagged tree has another digest, and no record ran it.
- **No package, chart, or model.** The Python distribution is built locally and refuses an
  upload to an index, the chart is installed from the checkout, and every operator
  acquires the model from the pinned revision and verifies its hash.

## Where the frozen evidence still describes the repository before this release

The register is inside the frozen pack, so it cannot record the release it is cut over,
in the same way a ledger inside the pack cannot state the pack's digest. These surfaces
are true of the repository as it was frozen, and are left as they are:

- **The register and the proof dashboard** list `a-v1-release-has-been-published` as
  not claimed, because "no release has been executed" and "the changelog holds unreleased
  changes only". Moving that row changes the register, and with it the pack digest; it is
  work for a change after the tag, under a new ledger.
- **The register** gives, as the reason `SECURITY.md` claims nothing, that "no private
  channel is published". This release names GitHub private vulnerability reporting there.
  The register's Markdown page, [the claim and evidence matrix](../testing/claim-evidence-matrix.md),
  shows both rows as the register states them.
- **The case study** lists a published release among what V1 does not have, and names a
  first release cut against the frozen pack as the step before anything new. It is bound
  to both digests and stays as published.

## Where the released tree differs from what was measured

- **The telemetry label `service.version`** from the local composition moved from
  `0.0.0` to `1.0.0` with the version, because the composition tool refuses a
  composition whose label is not the version `pyproject.toml` declares. At `bcad343`,
  the revision the baseline rerun ran, it was `0.0.0`. The rerun's own records do not
  quote the label; records of earlier runs do, and quote `0.0.0`. No figure on this page
  depends on it. The chart leaves the label empty unless a values file sets it, as
  before.
- **The InferOps API image** is built from the checkout, so an image built from the
  tagged tree has a digest no record ran, as [what is not published](#what-is-not-published)
  says.

## Compatibility and upgrading

This is the first release, so there is nothing to upgrade from. From here, InferOps
follows Semantic Versioning: a breaking change to a published contract, the API, the
chart's values contract, or a command's interface increments the major version. The
workload contract keeps its own version, `v1alpha1`, and
[its own changelog](../../contracts/CHANGELOG.md); the chart keeps its own version too.

## Security reporting

[The security policy](../../SECURITY.md) names GitHub's private vulnerability reporting
for this repository as the private channel. It is a setting on the hosting service: on
2026-09-27, when these notes were written, it read disabled, and
[the checklist](v1.0.0-checklist.md) refuses the tag until it reads enabled. No
acknowledgement window, remediation timeline, or backported fix is promised.
